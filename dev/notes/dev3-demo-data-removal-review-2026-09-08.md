### Why re-verify instead of reusing dev3's IDs

The dev3 cleanup already ran and was verified there on 2026-09-15 (see
below). Its `dev/tools/dev3_demo_data_cleanup.php` script hardcodes numeric
IDs specific to that database snapshot. Production has its own independent
auto-increment history, so those IDs are not guaranteed to point at the same
rows — reusing them blindly against a live store risks deleting the wrong
data. This document's own "Patch shape" section requires running the same
inventory queries against production and requiring "exact or
consciously-approved differences" before a production patch, so that's what
was done.

### Method

Read-only `SELECT`-only queries (no writes) were run directly against
production via `dev/tools/remote_db.sh`, which connects to the `[client]`
profile in `.local/remote-db.cnf` — confirmed to be `verifiedbota_magento2`
at `66.206.23.226`, the same production database used by `automated-tests`'
`[prod]` target.

### Backup taken before any write

Production has ~875 tables, ~165 of which are per-store index/replica tables
(`*_index_store<N>[_replica]`) generated by the 80 demo store views — these
are regenerable by Magento's indexer and were excluded. The remaining 710
source tables were backed up.

A single whole-database `mysqldump` repeatedly failed mid-transfer
(`TLS/SSL error: unexpected eof`, `Server has gone away`) — this environment
runs under WSL2, whose outbound NAT appears to drop long-idle/long-running
TCP connections after roughly two minutes. Splitting the dump into 6 chunks
(then one chunk further into 3 sub-chunks after it also failed) of ~40–140
tables each, each a fresh short connection, completed successfully.

- Location: `backups/prod-pre-demo-cleanup-20260923_163542/` (9 `.sql.gz` files)
- Verified: every one of the 710 target tables has exactly one `CREATE TABLE` across the chunk set, confirmed by diffing the dumped table names against the full expected list.
- Known, accepted exclusion: the `inventory_stock_1` view, same as the dev3 dump below — could not be read by `mysqldump`; its backing tables are present.
- Not backed up: production `pub/media` — this pass only had database credentials for production, not filesystem/server access. Not required by this script (it deletes no media files); a separate media backup is worth doing by whoever has hosting access if wanted as an extra safety net.

### Cleanup script

`dev/tools/prod_demo_data_cleanup_preflight.sql` (read-only checks) and
`dev/tools/prod_demo_data_cleanup_apply.sql` (the transactional deletes,
templated with a `-- FINAL_STATEMENT_PLACEHOLDER` swapped for `ROLLBACK;` on
a rehearsal pass and `COMMIT;` on the real pass) — run via
`dev/tools/remote_db.sh --file`, not a Magento PHP bootstrap script:
`dev/tools/dev3_demo_data_cleanup.php`'s approach (Magento
`Bootstrap`/`ResourceConnection`) resolves to `app/etc/env.php`'s connection,
which points at the local DDEV database, not production — a PHP-bootstrap
version would have silently run against the wrong database. The production
scripts use the same raw-SQL path already proven against production for
every read-only query above.

Sequence run, in order:
1. Preflight — all counts matched expected values.
2. Chunked backup (above).
3. Rehearsal (apply script + `ROLLBACK`) — deletes ran cleanly, post-delete sanity checks passed, then verified production was unchanged.
4. Apply script + `COMMIT` — applied for real.
5. Independent post-cleanup verification (fresh query, outside the transaction).

## Decision summary

The earlier audit is directionally useful, but is not safe to apply verbatim to production. Its counts have drifted and three important assumptions are now false:

1. The `Default` attribute set contains one current, explicitly protected product: ID `470` / SKU `vb-blog-media` / `VB Blog Media (do not delete) vb-blog-media`. Do not delete by attribute-set alone.
2. Only 9 of 33 reviews belong to demo products. Reviews `239`–`262` belong to live Kratom parents and must remain.
3. Every store group currently points at root category `2` (`Default Category`), including the live group. There are no separate demo roots to delete. Do not run the proposed category/root-category deletion phase.

## Patch shape for dev3, then production

Use a versioned Magento maintenance script/data patch which accepts only these explicit IDs, starts with a backup/dry-run report, deletes dependent sales and review rows before primary rows, and finishes with reindex/cache commands. Do not use a broad `DELETE` by attribute set, date, store name, or email domain.

Order:

1. Back up DB and media; run the script in dry-run mode and compare every count above.
2. Delete the 19 demo orders and all dependent invoice/shipment/credit-memo, payment, item, grid, and sales-link rows identified by the dry run.
3. Delete reviews `41,43,47,50–54,192` and their rating/detail/summary rows.
4. Delete customers `1–19` and their address/entity attribute rows.
5. Delete only the 67 enumerated products through Magento services (or a dependency-aware maintenance script), preserving `470`.
6. Remove store views, then groups, using the exact IDs above. Reconcile scoped configuration, URL rewrites, CMS page/store assignments, and widget/store assignments; do not delete CMS blocks.
7. Remove `Auto`, then the three enumerated attributes only after verifying no remaining product values/references.
8. Delete CMS pages `5–7`; keep page `8`.
9. Reindex, flush cache, and run storefront/admin smoke tests.

Before production, run the same inventory queries against production and require exact or consciously-approved differences. The production patch must refuse to run if protected product `470`, live store `111`, or Kratom review IDs are selected.
